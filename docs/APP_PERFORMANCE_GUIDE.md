# Loop 앱 전체 성능·트래픽·동시성 검증 가이드

작성·공식 문서 확인: 2026-09-18. 상태: 설계 및 실행 계획. 성능 측정·최적화 완료 보고서가 아니다.

## 1. 목표와 원칙

목표는 자연스러운 페이지 이동, 안정적인 스크롤, 중복 없는 데이터 처리, 트래픽 집중 시 예측 가능한 지연과 실패 처리다. 모든 기기·모든 부하에서 프레임 드랍이나 병목이 없음을 보장할 수는 없다. 지원 기기와 목표 부하를 정하고 반복 측정으로 검증한다.

- 앱 프레임 문제, 네트워크 지연, 서버 처리 한계를 별도로 측정한 뒤 같은 사용자 행동으로 연결한다.
- 최신 기술을 도입했다는 사실보다 개선 전후 수치와 정합성을 우선한다.
- 미측정 상태에서 isolate, 캐시, 큐, 서버 증설을 일괄 도입하지 않는다.
- 코드의 실행 순서를 바꾸는 최적화는 취소·실패·계정 변경·중복 요청까지 검증한다.
- 기존 [오프라인 캐시 정책](POST_OFFLINE_CACHE.md)을 유지한다. 목록 캐시를 상세·댓글 캐시로 오해하지 않는다.
- 서버의 읽기 부하 절차는 별도 저장소 `loop_server/docs/posts-load-test.md`, `loop_server/server.md`를 함께 참고한다. 두 저장소를 나란히 받지 않아도 문서 자체는 읽을 수 있도록 경로만 안내한다.

## 2. 현재 프로젝트와 점검 위치

아래는 파일 존재·일부 구현 확인 기준이다. 앱 전체 성능 감사를 완료했다는 뜻은 아니다.

| 범위 | 확인 파일/폴더 | 점검 질문 |
| --- | --- | --- |
| 앱 초기화·잠금 | `lib/main.dart`, `lib/src/features/app_lock/` | 초기화 로딩, 로그인, 잠금 화면이 서로 불필요하게 전환되는가? |
| 라우팅·탭 | `lib/src/core/router/router.dart` | indexedStack 탭 상태·뒤로 가기·중복 push가 적절한가? |

| 채팅 | `lib/src/features/chat/data/data_sources/socket/chat_socket_data_source.dart`, presentation/providers | 화면 왕복 후 구독·연결·메시지가 중복되는가? |

현재 pubspec에는 Dart ^3.9.2, Riverpod ^2.6.1, Dio ^5.9.2, go_router ^17.2.2, Drift ^2.31.0이 선언되어 있다. 이는 설치 확정 버전이 아니라 버전 제약이다. 실행 시 Flutter 버전과 pubspec.lock을 기록한다. 최신 문서 예제를 기존 SDK에서 그대로 사용할 수 있다고 가정하지 않는다.

## 3. 최신 기술을 적용하는 기준

| 기술·접근 | Loop 적용 방향 | 도입/변경 조건 |
| --- | --- | --- |
| Flutter DevTools·프레임 타이밍 | 가장 먼저 사용할 기본 측정 도구 | 실기기 profile 기준선 확보 |
| Impeller | 해당 Flutter·OS·GPU에서 실제 사용하는 렌더러 기록 | 엔진 변경으로 Dart 연산·네트워크 병목까지 해결된다고 기대하지 않음 |

| 취소·중복 요청 병합 | 의미 없는 읽기를 취소하고 동일 조회 결과 공유 | 사용자·권한·쿼리별 요청 범위 분리 |

| 제한된 동시 실행·멱등성 | 다중 업로드/작성에 명시적인 처리 상한 | 서버 계약·테스트 먼저 설계 |
| BullMQ·Transactional Outbox | 저장 이후 요약·알림 등 후속 작업 분리 후보 | DB 저장과 큐 등록 사이 유실, 재시도 중복을 해결해야 할 때 |
| k6 도착률 기반 부하 | 서버가 느려져도 유입이 계속되는 상황 검증 | autocannon 기준선 이후 도입 |
| OpenTelemetry 분산 추적 | 요청→DB→큐 구간 병목 연결 | 우선 서버 계측, 앱은 지원 SDK 검증 후 별도 선택 |
| 성능 회귀 자동화 | integration_test와 고정 실기기 결과 비교 | 수동 시나리오가 안정된 뒤 적용 |

Impeller의 지원·기본 활성 조건은 [공식 문서](https://docs.flutter.dev/perf/impeller)를 확인한다. Riverpod select는 변경 관심 범위를 줄이는 수단이며 모든 Provider에 기계적으로 적용하지 않는다. [Riverpod 공식 가이드](https://riverpod.dev/docs/how_to/select)

## 4. 측정 환경과 지표

### 공통 준비

1. 대표 Android 실기기와 iPhone을 선정한다. 가능하면 저사양 Android도 포함한다.
2. 기기·OS·주사율·전원 모드·발열, Flutter/패키지 버전, 커밋을 기록한다.
3. 테스트 계정과 데이터·캐시 상태, 서버 배포 환경, 네트워크 조건을 고정한다.
4. 민감 정보가 포함된 로그·HAR·프로파일은 공개하지 않는다.
5. debug는 기능 확인용, 성능 수치는 실기기 profile에서 수집한다. release에서도 최종 체감 동작을 확인한다.

```bash
flutter devices
flutter run --profile -d <실제_기기_ID>
```

실기기의 127.0.0.1은 개발 PC가 아니다. Android 에뮬레이터용 10.0.2.2도 실기기 주소가 아니다. 테스트용 API 주소/연결 방법을 별도로 설정하고 운영 서버로 연결하지 않는다.

### 나누어 기록할 시간

- 탭 → 첫 시각 반응: 누름 상태·진행 표시 등 즉각적인 피드백.
- 탭 → 대상 화면 첫 프레임: 라우팅과 기본 레이아웃.
- 탭 → 필요한 데이터 표시: API·파싱·상태 반영 포함.
- UI 시간 / Raster 시간 / 느린 프레임 비율: 렌더링 작업의 구간별 비용.
- API 왕복 시간 / 정상 응답률 / 요청 횟수 / 전송량.
- 메모리·GC·연결/구독 수와 화면 왕복 후 증가 추이.
- 작성 완료 시간 / 중복 행 수 / 후속 작업 완료 시간.

60Hz의 프레임 주기는 약 16.7ms, 120Hz는 약 8.3ms다. UI와 Raster 작업은 파이프라인이므로 두 값을 무조건 더해서 느린 프레임을 판정하지 않는다. 실제 주사율과 프레임 지표를 함께 기록한다. [DevTools Performance](https://docs.flutter.dev/tools/devtools/performance)

## 5. 화면 전환·프레임 드랍 테스트

### 재현 시나리오

각 시나리오를 최소 3회 반복한다. 첫 실행과 캐시가 데워진 반복 실행을 분리한다.

| ID | 행동 | 검증 |
| --- | --- | --- |
| UI-01 | 게시글 목록→상세→뒤로 가기 20회 | 이전 스크롤 위치, 페이지 전환 느린 프레임, 중복 API |
| UI-02 | 게시글 목록 30초 스크롤·10페이지 이상 조회 | 다음 페이지 도착 시 UI/Raster 급증, 메모리 증가 |
| UI-03 | 탭 전환 20회, 글자 크기 확대·가로 화면 | 불필요한 재로딩, overflow, 숨긴 탭의 지속 작업 |
| UI-04 | 작성→제출→목록 복귀 | 제출 피드백, 중복 push, 목록 전체 깜빡임 |
| UI-05 | 상세 진입 직후 뒤로 가기·다른 글 열기 | 오래된 응답 반영, dispose 후 상태 변경 |
| UI-06 | 알림으로 상세 진입·연타 | 올바른 복귀 경로, 중복 라우트·Hero tag, 잠금 유지 |
| UI-07 | 채팅/SSE/BLE/WebView 진입·종료 20회 | 타이머·구독·연결 잔존, 반복 이벤트 |
| UI-08 | 다크 모드·언어 변경, 앱 잠금·복귀 | 불필요한 루트 재생성, 잠금 해제 전 데이터 노출 |

### 측정 절차

1. DevTools Performance 기록을 시작한다.
2. 하나의 시나리오만 수행하고 종료한다.
3. 느린 프레임을 선택해 UI/Raster와 해당 타임라인을 확인한다.
4. 원인 후보가 rebuild/layout이면 상세 추적을 잠시 켠다. 추적 오버헤드가 있으므로 최종 비교는 동일한 기본 옵션으로 한다.
5. 스냅샷을 실행 ID와 함께 저장한다. Memory는 같은 왕복 시나리오로 별도 관찰한다.
6. 변경 하나를 적용한 뒤 같은 조건으로 반복한다.

### 자연스러운 이동을 위한 설계

- 서버 응답 전체를 기다린 후 이동하는 대신 대상 화면의 기본 구조를 먼저 보여줄지 기능별로 결정한다. 인증·권한 보호는 유지한다.
- 목록에서 받은 제목·썸네일은 진입 시 힌트로 활용할 수 있지만 서버 상세의 최신 권한·삭제 상태를 대체하지 않는다.
- 첫 로딩은 레이아웃 크기가 안정적인 placeholder, 추가 로딩은 기존 항목 유지, 오류는 해당 영역에 표시한다.
- push/go는 뒤로 가기 계약에 맞게 선택한다. 전환을 부드럽게 한다며 스택을 무조건 교체하지 않는다.
- 동일 행동의 중복 이동을 막고 Hero tag를 고유하게 유지한다.
- 기본 플랫폼 전환부터 시작한다. 과도한 전체 화면 fade/blur를 추가하지 않으며 시스템의 애니메이션 축소 설정을 존중한다.
- 숨긴 탭을 유지하는 것은 재진입에 유리하지만 메모리·구독 비용이 있다. 화면 상태 보존과 불필요한 작업 중단을 구분한다.
- 네트워크 완료로 기존 내용을 전체 spinner로 교체하거나 이미지 크기가 뒤늦게 바뀌는 전환을 피한다.

## 6. 앱 네트워크·트래픽 검증

DevTools Network는 Dart 통신의 요청 시간·상태·본문 등을 확인하는 도구다. 네이티브 SDK/WebView 전체 통신이 모두 보인다고 가정하지 않는다. 앱 한 대의 기록은 전체 사용자 트래픽이 아니다. Web은 브라우저 DevTools도 별도로 사용한다. [공식 Network 가이드](https://docs.flutter.dev/tools/devtools/network)

### 시나리오

- 페이지네이션 임계점에서 반복 스크롤: 같은 cursor가 동시에 여러 번 전송되는지 확인.
- 빠른 검색 입력·지우기: 최신 검색만 표시되는지, 취소된 요청이 에러 UI를 띄우지 않는지 확인.
- 여러 API가 동시에 401: refresh 공유·최대 재시도·최종 로그아웃·계정 변경 이후 결과 무효화 확인.
- 연결 지연·끊김·복구: 캐시 유지, 재시도 버튼, 자동 재시도 폭증 여부 확인.
- 429·503·Timeout: 즉시 무한 재시도하지 않는지, 서버 응답과 통신 오류를 구분하는지 확인.
- 요청 취소 후 서버가 이미 처리한 쓰기: 결과 불명 상태와 중복 방지 정책 확인.

### 최적화 순서

1. 의도하지 않은 호출을 제거한다. build 안의 API 호출, 구독 중복, 여러 이벤트의 동일 새로고침을 점검한다.
2. 같은 조회의 진행 중 Future 공유를 검토한다. 검색어·cursor·계정·권한을 요청 식별에 포함한다.
3. 불필요한 읽기는 Dio CancelToken으로 취소하고 요청 번호로 늦은 응답도 방어한다.
4. 동시 401 처리는 QueuedInterceptor 존재만으로 충분하다고 가정하지 않는다. refresh 한 번의 결과 공유, 이미 갱신된 토큰 재사용, refresh 자체 재시도 금지를 테스트한다.
5. 재시도는 요청 의미별로 제한한다. 읽기는 제한된 횟수·지수 백오프·jitter, 429는 Retry-After가 있으면 존중한다. 쓰기는 멱등 계약 없이 자동 재시도하지 않는다.
6. connect/send/receive timeout과 전체 작업 기한을 구분한다. receive timeout을 전체 작업 제한이라고 가정하지 않는다.
7. 로그는 토큰·본문을 제거하고 샘플링한다. 대량 console 출력 자체가 측정에 영향을 줄 수 있다.

취소·타임아웃·인터셉터 API는 설치 버전에 맞는 [Dio 문서](https://pub.dev/packages/dio)를 확인한다. 취소는 서버 작업 롤백을 뜻하지 않는다.

## 7. 화면·메모리 최적화 우선순위

- build 안의 정렬·큰 변환·반복 계산을 제거하고 변화하는 영역별 위젯을 분리한다.
- 측정된 불필요 rebuild에만 Riverpod select를 적용한다. 비교할 상태는 불변성을 유지한다.
- 긴 목록은 lazy builder/sliver를 사용한다. 무한 목록 안의 과도한 shrinkWrap·intrinsic layout을 피한다.
- 썸네일은 표시 크기에 맞는 원본/디코딩 크기를 사용한다. 프리패치는 근처 항목만 제한적으로 한다.
- blur·opacity·clip·그림자는 Raster 병목이 확인된 부분부터 줄인다. RepaintBoundary는 무조건 추가하지 말고 레이어·메모리 증가와 함께 비교한다.
- 목록 200개 영속 캐시 제한과 화면 메모리 제한은 다르다. 긴 스크롤은 페이지 윈도잉·스크롤 복원 정책을 별도 설계한다.
- 화면 수명에 맞게 subscription, timer, controller, HTTP stream을 정리한다. dispose만으로 외부 연결까지 자동 종료된다고 가정하지 않는다.

렌더링 조언은 [Flutter 성능 모범 사례](https://docs.flutter.dev/perf/best-practices)를 기준으로 적용한다.

CPU 프로파일에서 큰 파싱·압축·정렬이 확인되면 isolate를 고려한다. await는 CPU 작업을 다른 isolate로 옮기지 않는다. 작은 데이터는 전달/생성 비용이 더 클 수 있다. 단순 네트워크 I/O나 모든 Future를 isolate로 옮기지 않는다. Web의 compute는 별도 병렬 isolate를 보장하지 않는다. [Flutter isolates](https://docs.flutter.dev/perf/isolates)

## 8. 사람이 몰리는 상황의 서버·앱 통합 테스트

### 안전 조건

- 격리된 테스트 DB·Redis·계정으로 실행한다. 특히 쓰기 부하 전에 FCM·AI·이메일·외부 업로드의 실제 호출과 요금을 차단/대체한다.
- 서버의 현재 전역 60초당 100회 제한은 용량 측정과 별도로 검증한다. 테스트 전용 조정만 허용하고 운영 방어는 유지한다.
- 앱은 사용자 체감 측정용으로 1~몇 대를 사용하고, 다수 요청은 별도 부하 도구로 만든다.
- 부하 생성기와 서버의 자원을 구분한다. 로컬 PC가 먼저 포화될 수 있다.
- DB 삭제·Redis 전체 삭제로 테스트를 초기화하지 않는다. 테스트 실행 ID로 생성 데이터를 추적한다.

### 단계

1. 서버 부하 없는 상태에서 UI-01/UI-02와 API 기준선을 기록한다.
2. 목록 읽기 동시 연결 1→10→50→100을 단계적으로 측정한다. 오류가 늘면 중단하고 원인을 확인한다.
3. 동일한 부하 중 실제 앱에서 같은 시나리오를 반복한다.
4. 트래픽 모델을 목록·상세·댓글 조회·작성으로 확장한다. 예시 비율 60/25/10/5는 가정일 뿐 운영 분석 수치가 아니다.
5. 인기 게시글에 요청을 집중시키는 경우와 여러 ID로 분산시키는 경우를 따로 측정한다.
6. 순간 급증·지속 부하·복구를 분리한다. 다음 연결 수준은 이전 결과가 안정적일 때만 진행한다.

고정 연결 모델은 응답이 느려지면 다음 요청 유입도 줄어든다. 기준선 이후 k6 arrival-rate 시나리오로 지속 유입을 검증하며 목표/실제 도착률과 dropped iterations를 함께 기록한다. 도구가 요청을 충분히 만들지 못했다면 서버가 목표를 처리했다고 판단하지 않는다. [k6 open/closed 모델](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/)

### 해석

| 증상 | 먼저 확인할 구간 |
| --- | --- |
| API 느림, 화면 애니메이션 부드러움 | 서버·네트워크·캐시·DB 대기 |
| API 빠름, 응답 직후 UI 프레임 급증 | 파싱·상태 반영·목록 갱신 |
| UI 시간 낮음, Raster 높음 | 이미지·효과·GPU 작업 |
| 정상 처리량 정체, p99 급증 | 서버/DB/부하 생성기 포화 또는 대기 |
| 화면 왕복할수록 메모리·이벤트 증가 | 구독·페이지 상태·이미지 캐시 수명 |
| 빠른 429가 대부분 | 처리 성능이 아니라 요청 제한 동작 |

## 9. 여러 게시글 작성과 동시 요청 정합성

버튼 연타, 한 사용자의 여러 글 작성, 여러 사용자의 동시 작성은 서로 다른 테스트다.

### 앱 측 설계

- 단일 제출은 in-flight guard로 연타 방지. 초안은 실패·화면 복귀 때 보존한다.
- 여러 글/파일은 개별 상태(대기·전송 중·성공·실패·결과 확인 필요)를 갖고 제한된 개수만 병렬 실행한다. 병렬 2~3개는 시작 실험값이지 정답이 아니다.
- 같은 작성 의도를 재시도할 때 같은 멱등 키를 사용한다. 다른 글은 다른 키를 사용한다.
- 타임아웃은 서버 저장 실패가 확정된 상태가 아니다. 결과 조회/같은 키 재시도로 확인하고 무조건 새 키로 재전송하지 않는다.
- optimistic UI를 쓰면 임시 항목을 서버 ID로 치환하고 실패 상태를 명확히 표시한다. 서버 확인 전에 영구 성공으로 표시하지 않는다.
- 오프라인 작성 큐는 별도 기능이다. 현재 목록 캐시가 이를 제공하지 않는다. 계정 분리·용량·보존기간·업로드 중단 정책이 필요하다.

### 서버 측 계약 — 향후 구현 대상

1. 요청마다 인증·인가·크기 제한을 검증한다.
2. (사용자, 작업 종류, 멱등 키)에 DB unique 제약을 두어 동시 중복도 막는다. 메모리 플래그나 Redis 임시 키만으로 최종 정합성을 보장하지 않는다.
3. 같은 키·다른 payload는 충돌로 거부한다. 처리 중 응답, 키 보존기간, 결과 재조회 계약을 정의한다.
4. 게시글과 필요한 관계 변경을 짧은 트랜잭션으로 처리한다. 중복 검사 후 insert를 별도 무잠금 작업으로 나누지 않는다.
5. 카운터는 원자적 갱신, 충돌하는 수정은 버전/낙관적 잠금 등으로 보호한다. DB 제약은 마지막 방어선이다. [PostgreSQL 제약 문서](https://www.postgresql.org/docs/current/ddl-constraints.html)
6. AI·대량 알림·이미지 변환은 측정에 따라 큐로 분리한다. 201 저장 완료와 202 작업 접수 의미를 혼동하지 않는다.
7. 저장 후 큐 등록 사이 실패는 outbox 같은 내구성 있는 전달 설계로 보완한다. 워커는 중복 실행될 수 있으므로 결과·알림의 멱등성도 구현한다. [BullMQ 멱등 작업](https://docs.bullmq.io/patterns/idempotent-jobs)
8. 워커 동시성·외부 API 제한·큐 대기시간·재시도 한도·최종 실패 복구를 관리한다. 큐는 처리 용량을 무한히 만들지 않는다.

현재 서버 PostsService.create는 최초 저장 뒤 AI 요약 호출을 await하고 다시 저장한다. 그 뒤 캐시를 무효화하고 알림 작업을 추가하며, 큐 등록 오류는 catch에서 무시한다. 이는 **점검된 현재 코드**이며 위 멱등성/outbox 설계가 이미 구현됐다는 뜻이 아니다. 외부 요약 대기와 저장 후 실패·작업 유실은 동시 작성 테스트의 우선 확인 대상이다.

### 반드시 검증할 사례

| 사례 | 기대 결과 |
| --- | --- |
| 동일 키로 10개 동시 제출 | 게시글 1개, 정해진 동일 결과/처리 중 응답 |
| 다른 키로 N개 제출 | 성공으로 확정된 작업 수만큼 저장, 누락·덮어쓰기 없음 |
| 같은 키·다른 내용 | 충돌 거부, 기존 데이터 유지 |
| 저장 후 응답 유실 | 같은 키 재확인 시 중복 글 없음 |
| 일부 파일/글만 실패 | 성공 항목 재작성 없이 실패 항목만 재시도 |
| 큐 재시도·워커 재시작 | 후속 결과/알림 중복 방지, 실패 작업 추적 가능 |
| 작성 중 계정 변경 | 이전 계정 결과가 새 계정 화면·초안을 덮어쓰지 않음 |
| 동시 수정·삭제 | 정해진 충돌 정책, 잘못된 댓글 수·고아 데이터 없음 |

DB 저장 건수와 API 성공 수뿐 아니라 결과 불명 요청의 최종 상태도 대조한다. HTTP 부하 도구의 빠른 성공만으로 정합성을 통과시키지 않는다.

## 10. 병목별 최적화와 과부하 대응

- DB: 실제 느린 쿼리·실행 계획부터 확인, N+1·필요 없는 컬럼·정렬/필터 인덱스 개선. pool은 DB 전체 연결 예산 안에서 조정한다.
- 캐시: 적중률·만료 순간 요청 집중을 측정한다. 필요한 경우 요청 병합·TTL 분산·stale 정책을 설계하고 계정/권한/삭제 정합성을 유지한다.
- 서버: 무거운 동기 CPU 작업을 분리하고 로그량·이벤트 루프 지연을 측정한다. 수평 확장 전 상태·연결·요청 제한의 공유 범위를 확인한다.
- 큐: 처리량뿐 아니라 가장 오래된 작업의 대기시간과 backlog 증가율을 본다. 입력을 무제한 수용하지 않는다.
- 앱: 재시도 횟수와 병렬 수를 제한하고 과부하 시 기존 읽기 화면/초안을 유지한다. 진행 상태를 사실대로 표시한다.
- 전체: 예측 가능한 429/503과 재시도 안내를 제공한다. 무조건 오래 기다리거나 성공처럼 보이게 만드는 것은 최적화가 아니다.

## 11. 자동화·운영 관찰·완료 기준

### 자동화 단계

1. 단위 테스트: 오래된 응답 무시, 취소, refresh 병합, 제출 중복 방지, 계정 변경, 캐시 무효화.
2. 위젯 테스트: 로딩 중 기존 목록 유지, 실패 초안 보존, 뒤로 가기, 중복 네비게이션.
3. integration_test: 고정 동작의 페이지 왕복·스크롤 프레임 자료 수집. [Flutter 성능 통합 테스트](https://docs.flutter.dev/cookbook/testing/integration/profiling)
4. 서버 통합 테스트: 실제 테스트 PostgreSQL의 트랜잭션·unique 경합·멱등 재시도.
5. 성능 테스트: 전용 기기/러너에서 같은 빌드·데이터로 전후 비교. 공유 CI 머신의 1회 수치만으로 성능 회귀를 확정하지 않는다.

### 관찰

앱 요청 ID와 서버 trace를 연결해 HTTP→DB→큐 구간을 추적하는 것을 검토한다. trace와 요청 멱등 키는 목적이 다르다. 사용자별 데이터를 metric label로 무제한 넣지 않는다. 토큰·본문은 제외하고 샘플링·보존기간·비용을 정한다. OpenTelemetry는 추적 모델의 기반이지 Flutter 자동 계측 완성품을 보장하는 이름이 아니다. [OpenTelemetry traces](https://opentelemetry.io/docs/concepts/signals/traces/)

### 결과 템플릿

| 실행 ID/커밋 | 기기/환경 | 시나리오/캐시 | UI·Raster p99/느린 프레임 비율 | 첫 표시/데이터 완료 | API p99/오류 | 메모리 | 정합성 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 미측정 | 미측정 | 미측정 | 미측정 | 미측정 | 미측정 | 미측정 | 미검증 |

- 목표는 기기군·화면·부하별로 정한다. 평균 FPS 하나로 통과시키지 않는다.
- 느린 프레임 비율은 기록된 프레임 수 대비 기준 초과 프레임 수로 정의하고 측정 도구/주사율을 남긴다.
- percentile은 실행별로 기록한다. 여러 p99의 단순 평균을 전체 p99라고 부르지 않는다.
- 완료는 동일 조건 3회 이상 비교, 목표 지연/오류 충족, 누락·중복 없음, 복구 동작·원본 기록 확인으로 판단한다.
- 실제 기기 테스트 전에는 “프레임 드랍 없음”, 부하 테스트 전에는 “대규모 사용자 대응 완료”라고 기록하지 않는다.

## 12. 실행 우선순위

- [ ] 1단계: 실제 기기·빌드·서버 대상 고정, UI-01/UI-02 기준선 수집.
- [ ] 2단계: Network에서 중복 요청·refresh·페이지네이션 경합 점검.
- [ ] 3단계: 느린 UI/Raster 프레임의 원인 하나씩 개선.
- [ ] 4단계: 서버 읽기 부하와 앱 체감 동작을 함께 측정.
- [ ] 5단계: 격리 환경의 동시 작성·멱등 API 계약 설계 및 테스트.
- [ ] 6단계: 필요한 AI/알림 비동기화·작업 유실 복구 적용.
- [ ] 7단계: 장시간·급증·복구 시나리오, 성능 회귀 자동화.
- [ ] 8단계: 목표 부하를 넘으면 제한/저하 전략 및 증설 효과 검증.

첫 실행은 실기기 profile에서 “목록→상세→뒤로 가기”와 “30초 스크롤”이다. 문서만 추가한 현재에는 어떤 성능 수치도 검증 완료로 취급하지 않는다.
