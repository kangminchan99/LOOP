# 사용자 차단·해제 앱 연동 계획

작성: 2026-10-27. 상태: 문서 단계. 모델·API·Provider·화면·로컬 DB 변경과 검증을 완료한 문서가 아니다.

## 1. 기능 범위와 기준 문서

로그인한 사용자가 상대 계정을 차단하고, 설정의 차단한 사용자 목록에서 해제한다. 게시글·검색·댓글은 서버가 차단 조건을 먼저 적용한 뒤 페이지네이션한다.

서버 계약: [서버 차단 설계](../../loop_server/docs/user-blocking.md). 저장소를 따로 체크아웃했다면 `loop_server/docs/user-blocking.md`를 함께 확인한다.

- 내가 차단한 작성자의 콘텐츠는 내 목록에서 제외하고 상세·알림 링크도 서버 정책을 적용한다.
- 차단 관리 목록에서는 대상의 최소 프로필을 표시해야 해제할 수 있다. 이 관리 목록에 차단 필터를 다시 적용하지 않는다.
- 차단은 사용자나 콘텐츠 삭제·계정 제재가 아니다. 상대방에게 차단 알림을 보내지 않는다.
- 게시판은 내 차단 방향 기준이다. 채팅은 어느 방향이든 차단 관계가 있으면 양쪽의 방 접근·신규 전송을 제한한다.
- 비로그인 공개 게시판은 유지한다. 로그인 차단은 공개 콘텐츠 자체의 비밀성을 보장하는 기능이 아니다.
- 신고·관리자 제재·그룹 채팅 정책은 이번 범위에 포함하지 않는다.

| API 예정 | 앱 사용 위치 |
| --- | --- |
| PUT `/users/me/blocks/:targetUserId` | 작성자 차단. 기존 관계도 같은 목표 상태로 수렴 |
| DELETE `/users/me/blocks/:targetUserId` | 차단 해제. 성공은 본문 없는 204 |
| GET `/users/me/blocks?limit=20&cursor=...` | 차단 목록·더 보기·새로고침 |

목록 응답은 `{ items, nextCursor, hasNext }`, 항목은 `{ blockId, userId, nickname, profileImageUrl, blockedAt }`로 계획한다. 실제 DTO 구현 후 nullable·날짜·숫자 형식을 확인한다. 닉네임이나 화면 인덱스로 대상을 식별하지 않는다.

## 2. 현재 코드에서 확인한 준비 사항

| 현재 파일 | 상태·영향 |
| --- | --- |
| `settings/presentation/models/settings_menu.dart` | blockedUsers 메뉴가 있으나 isImplemented=false |
| `post/domain/models/post_list_model.dart` | 목록에 authorId 없음 |
| `core/database/tables/cached_posts.dart` | postId 단일 키, 계정·작성자·가시성 버전 없음 |
| `post/data/data_sources/local/post_local_data_source.dart` | revision/session으로 오래된 저장 방어. 가시성 변경과 연결 필요 |
| `post/presentation/providers/post_list/post_list_notifier.dart` | requestId·캐시 선표시·페이지 로딩 흐름이 있음. 새 정책과 함께 유지 |
| `comments/domain/models/comment_model.dart` | 댓글 authorId가 이미 있음 |
| `post/domain/models/post_response_model.dart` | 상세 authorId가 이미 있음 |
| `core/network/dio_network.dart` | 토큰 첨부·401 갱신. 인증 실패 후 익명 콘텐츠로 전환되지 않게 확인 |

서버 목록 DTO에 authorId를 추가한 뒤 앱 모델·JSON 생성 코드·변환·캐시 경로를 함께 정리한다. 없는 ID를 임의의 0이나 닉네임으로 대체하지 않는다.

## 3. 예정 기능 구조

```text
lib/src/features/user_blocks/
├── domain/
│   ├── models/
│   ├── repositories/            # AbstractUserBlocksRepository
│   └── usecases/                # 차단·해제·목록 조회
├── data/
│   ├── data_sources/remote/     # UserBlocksApi
│   └── repositories/
└── presentation/
    ├── providers/
    ├── pages/                   # BlockedUsersPage
    └── widgets/
```

Page → Notifier → UseCase → 추상 Repository → 구현 → API 구조와 기존 Freezed/Riverpod 패턴을 따른다. 화면에서 Dio·secure storage·Drift를 직접 조작하지 않는다. 설치 버전을 확인하고 새 라이브러리는 필요할 때만 검토한다.
다른 기능의 private 상태를 직접 조작하지 않고 공개 Provider·가시성 변경 이벤트 또는 조정 UseCase로 영향받는 상태를 갱신한다.

## 4. 차단·해제 흐름과 요청 수명

1. 상세·댓글 작성자 메뉴에서 실제 authorId로 대상을 선택한다. 본인 메뉴에는 차단을 표시하지 않는다.
2. 확인창에 대상과 숨김·채팅 제한 효과를 안내한다. 확인 전에는 요청하지 않는다.
3. 요청 중 대상별 버튼을 막아 연속 제출을 방지한다.
4. 서버가 성공을 확인하면 가시성 세대를 증가시키고 차단 전 요청·캐시 쓰기를 무효화한다.
5. 영향받는 목록·검색·상세·댓글·채팅·알림을 정리하고 첫 페이지부터 재조회한다. 뒤로 가기·IndexedStack 보존 화면에도 적용한다.
6. 실패하면 성공으로 표시하지 않는다. 응답 유실은 미확정으로 안내하고 동일 목표의 명시적 PUT/DELETE 재요청으로 수렴할 수 있다.
7. 해제 후 차단 관리 목록과 콘텐츠 목록을 첫 페이지부터 다시 조회한다. 원래 콘텐츠를 새로 생성하지 않는다.

일부 차단 목록 페이지만 조회하고 대상이 없다고 미차단으로 단정하지 않는다. 전체 목록 부재를 증명하는 별도 계약 없이 첫 페이지의 항목만으로 판단하지 않는다.
요청마다 계정·세션·목록 세대 번호를 확인해 로그아웃·다른 계정 전환·화면 종료 후 오래된 응답을 버린다. 차단 후 최신 조회가 실패해도 이전 차단 콘텐츠를 되살리지 않는다.

## 5. 페이지네이션

- 서버가 차단 제외 → 커서 조건 → 정렬 → limit+1을 적용한다. 앱에서 페이지를 받은 뒤 항목만 제거하고 기존 hasNext/cursor를 유지하는 방식으로 끝내지 않는다.
- 차단·해제는 목록 조건 변경이므로 이전 nextCursor·누적 페이지를 초기화한다. 해제로 앞쪽에 다시 보이는 글은 기존 커서를 이어 쓰면 빠질 수 있다.
- 추가 조회 실패는 해당 커서를 유지하고 재시도한다. 첫 조회/새로고침 실패와 다음 페이지 실패를 구분한다.
- ID 중복 방어는 유지하되 서버 커서를 합성하거나 잘못된 누락을 앱에서 보정하지 않는다.
- 차단 관리 목록도 기본 20·최대 50의 서버 커서를 사용한다. 해제 후 첫 페이지를 다시 조회해 빈 페이지·hasNext를 정리한다.
- 차단 때문에 표시할 글이 없는 상태와 네트워크 오류를 구분한다.
- 관계가 고정된 전체 순회와 조회 중 관계가 변경되는 상황은 별도 테스트한다. 변경 중 전체 스냅샷을 보장한다고 표현하지 않는다.

## 6. 오프라인 캐시와 계정 전환

기존 디스크 캐시는 공개 목록 스냅샷이며 개인 가시성을 증명할 정보가 없다. 초기 연동 정책은 다음과 같다.

- 비로그인 공개 캐시는 기존 TTL·최대 200개 정책을 유지한다.
- 로그인 후에는 검증된 계정별 가시성 정보가 없는 디스크 fallback을 사용하지 않는다. 이전 공개 스냅샷을 먼저 그리지 않는다.
- 차단·해제 성공 시 캐시 revision과 영향받는 메모리 상태를 무효화한다. 작성자를 모르는 행을 닉네임으로 선택 삭제하지 않는다.
- 안전한 선택 삭제가 어려우면 해당 개인 스냅샷을 폐기하고 첫 페이지를 다시 조회한다. 전체 앱 Provider를 무조건 초기화하지 않는다.
- 캐시 정리·재조회 실패는 서버 차단의 취소가 아니다. 안전한 숨김 상태와 재시도 안내를 유지한다.
- 로그인·로그아웃·계정 변경 시 가시성 세션과 진행 중 응답을 무효화한다. A의 차단 목록이나 개인 캐시를 B에게 사용하지 않는다.
- 다른 기기의 변경은 재개·새로고침·재접속 때 확인한다. 오프라인 기기에 즉시 원격 반영한다고 보장하지 않는다.

개인화 오프라인 목록을 유지하려면 계정 소유·authorId·가시성 버전의 스키마, Drift schemaVersion과 업그레이드 테스트, 기존 작성자 미상 행의 폐기·재조회 정책을 먼저 구현한다. 차단 ID 전체를 앱 시작마다 무제한 로드하는 방식은 기본 설계로 쓰지 않는다.

## 7. UI·라우팅·채팅·알림

- 로그인 상태에서만 설정의 blockedUsers 메뉴를 활성화한다. 직접 경로 접근도 로그인 상태를 검사한다.
- 목록 행은 프로필 placeholder·닉네임·해제 버튼을 제공한다. 긴 이름·큰 글자·다크 모드·작은 화면을 지원한다.
- 로딩·빈 목록·더 보기·새로고침·오류·재시도를 구분한다. 조회 실패를 빈 차단 목록으로 바꾸지 않는다.
- 문구는 `lib/l10n/app_ko.arb`, `app_en.arb`에 추가하고 gen-l10n으로 생성한다.
- router_path.dart/router.dart와 설정의 SettingsMenuId.blockedUsers, _openMenu를 연결한다. 복귀 가능한 목록 이동은 기존 push 정책을 따른다.
- 차단되면 영향받는 1:1 방·room 구독을 정리한다. 서버도 join/read/send를 검사한다. 다른 상대와의 채팅을 위해 전체 소켓 연결은 유지한다.
- 차단 전 저장됐거나 네트워크에 실린 메시지는 도착할 수 있다. 현재 가시성·세션 기준으로 화면 반영을 막는다.
- 알림 목록·미읽음 수·딥링크는 서버 필터와 일치해야 한다. FCM에 이미 전달된 알림을 차단으로 회수한다고 표현하지 않는다.

## 8. 구현 순서와 검증

1. 서버 테이블·API·선택적 인증·SQL 필터·캐시 정책을 구현하고 격리 통합 테스트로 검증.
2. 실제 DTO로 모델·API·Repository·UseCase와 응답/실패 매핑 작성.
3. 세션별 차단 목록 State/Notifier/Provider와 다음 페이지·조회 종류별 재시도 작성.
4. 콘텐츠 가시성 조정과 공개 캐시 선표시의 로그인 경계 보완.
5. 상세·댓글 메뉴·확인창, 차단 목록·해제·라우터·다국어 연결.
6. 서버와 함께 채팅·알림 정책을 적용하고 UI·네트워크·경합 회귀 검증.

필수 검증:

- A의 차단이 A 콘텐츠 목록에 반영되며 C·익명의 정책은 유지되는지.
- 관리 목록에서 B를 해제하면 첫 페이지 재조회로 콘텐츠가 복귀하는지.
- 원본 페이지의 차단 작성자 비중 0%·일부·100%, 동일 작성 시각, 모두 차단된 목록에서 커서와 빈 상태가 정확한지.
- 20개 이상 차단 목록의 더 보기·마지막 페이지·중간 해제·대상 탈퇴 확인.
- 차단 이전 요청 지연과 오래된 응답의 메모리·디스크 재삽입 방지.
- 오프라인·실패·결과 미확정, 작업 중 계정 변경·같은 계정 재로그인·뒤로 가기·탭 보존 확인.
- 기존 캐시에서 업그레이드 후 로그인 사용자에게 검증되지 않은 공개 스냅샷이 노출되지 않는지.
- 기존 방·실시간 메시지·양방향 차단·한쪽만 해제·알림 미읽음 수·딥링크 확인.
- 위젯 테스트로 다국어·확인 전 무요청·중복 클릭·테마·긴 문구를 확인하고 실기기 profile에서 긴 목록·재조회 프레임을 측정.

차단 API만 연결한 상태를 앱 전체 차단 완료로 보고하지 않는다. 관련 문서: [아키텍처](../CLAUDE.md), [오프라인 캐시](POST_OFFLINE_CACHE.md), [앱 성능](APP_PERFORMANCE_GUIDE.md).
